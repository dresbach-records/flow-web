## 3. Visão

Construir o FLOW como uma plataforma digital social moderna, escalável, segura, multiplataforma e orientada à comunidade, combinando experiência social, comunicação, descoberta de conteúdo, comunidades e serviços digitais em uma infraestrutura tecnológica profissional.

O FLOW deverá evoluir de forma sustentável, com arquitetura preparada para crescimento de usuários, aumento de tráfego, novas funcionalidades, integrações e expansão comercial.

## 4. Missão

Desenvolver uma experiência digital brasileira que conecte pessoas, comunidades e conteúdo por meio de uma plataforma confiável, intuitiva, acessível e tecnologicamente preparada para crescimento.

## 5. Propósito

Criar uma plataforma em que pessoas possam participar, comunicar-se, descobrir conteúdos, formar comunidades e utilizar recursos digitais em um ambiente concebido com foco em experiência, segurança, privacidade e evolução contínua.

## 11. Arquitetura de produto

A construção deverá favorecer separação de responsabilidades.

Uma referência conceitual:

```text
FLOW
├── Public Web
├── Authentication
├── Consent
├── Social Application
├── Admin
├── API
├── Backend
├── Data
├── Infrastructure
└── PWA
```

Cada domínio deverá possuir responsabilidades claramente delimitadas.

Componentes visuais deverão ser reutilizáveis e não deverão concentrar regras de negócio que pertençam a serviços, hooks, casos de uso ou camadas apropriadas.

## 12. Componentização

O FLOW deverá evitar páginas monolíticas.

Sempre que tecnicamente apropriado:

```text
Page
 ├── Layout
 ├── Section
 │   ├── Component
 │   ├── Component
 │   └── Component
 └── Feature
     ├── Hook
     ├── Service
     └── State
```

Cada componente deverá possuir responsabilidade clara, API previsível e possibilidade de reutilização.

### CSS

A organização visual deverá acompanhar a componentização.

Quando a arquitetura do componente exigir estilos próprios, o componente deverá possuir sua própria pasta e seu CSS associado, mantendo a responsabilidade visual próxima ao componente.

Exemplo:

```text
components/
└── PostCard/
    ├── PostCard.tsx
    ├── PostCard.css
    ├── PostCard.types.ts
    └── index.ts
```

A importação do componente deverá trazer seus estilos conforme o padrão adotado pelo projeto.

Não deverá existir concentração indiscriminada de todo o CSS da aplicação em um único arquivo quando isso prejudicar isolamento, manutenção ou reutilização.

## 13. Funcionalidade real

O FLOW não deverá utilizar conteúdo mockado como substituição permanente de funcionalidades reais.

Mocks poderão existir exclusivamente quando:

- estiverem explicitamente identificados;
- forem necessários para testes;
- forem usados em desenvolvimento controlado;
- houver tarefa definida para substituição;
- não forem confundidos com dados de produção.

Uma funcionalidade considerada concluída deverá possuir integração real com o serviço correspondente quando o backend já estiver disponível.

## 14. Firebase e infraestrutura existente

## 17. Consentimento e acesso à plataforma

O fluxo de cadastro deverá contemplar a etapa de consentimento/aceite exigida pelo produto.

Quando o aceite for requisito obrigatório para acesso à aplicação autenticada, o sistema deverá:

1. identificar que o usuário ainda não concluiu o aceite;
2. apresentar o conteúdo aplicável;
3. permitir leitura;
4. registrar o aceite de forma auditável;
5. liberar o acesso após o aceite;
6. impedir acesso quando o aceite obrigatório não ocorrer;
7. encerrar a sessão quando essa for a regra operacional definida;
8. informar claramente ao usuário o motivo da interrupção;
9. permitir novo login e nova tentativa conforme as regras do produto.

O registro deverá conter os elementos de auditoria definidos pelo modelo de dados e pelas políticas jurídicas aplicáveis, como versão do documento, data/hora e identificação da conta, quando legalmente apropriado.

## 23. Critérios de sucesso

Uma funcionalidade não deverá ser considerada concluída apenas porque sua tela aparece.

O sucesso deverá considerar:

```text
Interface
+ Estado
+ Interação
+ Backend/API
+ Persistência
+ Segurança
+ Tratamento de erro
+ Loading
+ Empty state
+ Testes
+ Responsividade
+ Acessibilidade
+ Observabilidade
= Funcionalidade pronta
```
